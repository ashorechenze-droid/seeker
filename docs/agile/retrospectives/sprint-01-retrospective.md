# Sprint 01 Retrospective

- 日期：2026-07-13
- 范围：Common 层、架构证据和敏捷过程证据

## 做得好的事情

- 先检查真实重复能力，再建立 Common，避免产生空包或万能工具类；
- 使用 ArchUnit 把文档中的依赖方向变成持续执行的规则；
- Review 引用真实测试数量和质量指标，没有只写笼统的“测试通过”；
- 对历史阶段只引用 Git、`plan.md`、ADR 和既有测试，不补写不存在的 Scrum 仪式。

## 遇到的问题

1. 原项目按 ports/adapters 组织，课程使用 UI/BLL/DAL/Model/Common 术语，两套术语之间缺少显式映射。
2. SHA-256 与文本清理在多个区域存在小规模重复，但此前没有稳定的 Common 边界。
3. 完整构建持续输出 Log4j2 缺少实现的警告，降低日志信噪比。

## 原因分析

- 架构主要面向实际变化和依赖方向设计，课程验收术语没有同步进入项目文档；
- 团队倾向把辅助方法放在调用者附近，随着功能增长才出现明确的跨区域复用；
- 传递依赖带入 Log4j2 API，但项目只显式配置了 `slf4j-nop`，日志桥接策略没有形成单独决策。

## 下一迭代改进行动

| 行动 | 负责人 | 完成条件 |
| --- | --- | --- |
| 评估并消除 Log4j2 provider 警告 | 项目开发者 | `mvn test` 不再输出 provider 警告，且无新增敏感日志 |
| 为后续功能在编码前补用户故事与 Given/When/Then | 项目开发者 | 下一项功能提交前已进入 Product Backlog 和 Sprint |
| 每次新增 Common API 时复核两个以上真实调用区域 | 项目开发者 | Review 中列出调用区域，ArchUnit 保持通过 |

## 要保持的实践

- 小步修改后先运行快速测试，再运行完整质量门禁；
- ADR、需求追踪、Backlog 和测试证据同步更新；
- 不把领域辅助类仅为了目录整齐搬入 Common。
